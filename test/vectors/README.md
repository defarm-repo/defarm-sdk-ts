# Conformance vectors (engines#591)

`rust-oracle.json` is **generated by the Rust reference implementation** — the oracle of the
wire format. Generator: `item-registry/tests/ts_conformance_vector_gen.rs` in the engines repo
(engines PR #606; a reference copy lives in `../../conformance/`). The TypeScript suite
(`test/conformance.test.ts`) replays the vectors and demands byte-for-byte equality.

Current vector set (5):

1. `envelope-basico-1-destinatario` — envelope + canonical AAD + key binding.
2. `envelope-3-destinatarios-fora-de-ordem` — recipients passed out of order; the sealer
   signature only verifies if the consumer reproduces the canonical wrap ordering.
3. `conteudo-json-unicode` — JSON content with accents + emoji (UTF-8 and JCS escapes
   end to end).
4. `api-response-do-serializer` — a `RecipientSealedField` serialized by the REAL Rust
   serializer; the SDK pins API field names here, not in prose (the sdk-ts#1 blocker class).
5. `cross-key-chave-gerada-pelo-sdk` — the recipient key pair was generated by THIS SDK
   (`@noble/curves`) and Rust sealed to it: catches X25519 generation/clamping divergence
   (issue #5).

To regenerate (in an engines checkout):

```bash
# optional, for the cross-key vector — generate a pair with this SDK first:
node --input-type=module -e "import {x25519} from '@noble/curves/ed25519';
const priv=crypto.getRandomValues(new Uint8Array(32));
const b64=b=>Buffer.from(b).toString('base64');
console.log('export TS_RECIPIENT_PRIV='+b64(priv));
console.log('export TS_RECIPIENT_PUB='+b64(x25519.getPublicKey(priv)));"

VECTOR_OUT=$PWD/vectors.json SQLX_OFFLINE=true \
  cargo test -p item-registry --test ts_conformance_vector_gen -- --nocapture
```

Private keys inside the vectors are FIXTURES (deterministic seeds, or throwaway pairs generated
just for the vector) — disposable by construction, never real keys.

**No asserting vectors here = the suite FAILS** (issues #2/#9): a green run always means
conformance actually executed.
